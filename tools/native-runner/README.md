# 無料の使い捨て環境でのSupabase実結合・復元試験

専用ブランチ `ci/v4-native-validation-20261029` の変更だけが起動条件。
公開リポジトリの標準 `ubuntu-24.04` ランナーを使い、成果物/キャッシュの保存や有料ランナーを使わない。
mainへのマージ、Pages公開、本番Secrets、本番接続、実データ輸出は含まない。
リポジトリが非公開ならジョブもコントローラーも停止する。公開状態の変更時は料金条件を再確認する。

## 構成

- CLI 2.122.0をlockfileで固定し、lifecycle scriptなしで導入する。
- 専用一時ディレクトリと `SUPABASE_HOME` を使い、実験的な公式nativeランタイムを非rootで起動する。
- API/DB接続先はループバックに限定。Authのメール送信、Edge、通知worker、cronは導入しない。
- 新規ローカル環境のAuth所有者ロールを移行担当ロールに付与して、取得済みAuthトリガーを再構築する。本番権限の変更案ではない。
- アプリDDLと6件の修正候補SQLを、空の架空DB内でだけCOMMITして試す。原本SQLのROLLBACKは保持する。
- 架空ユーザーの実パスワードログイン、PostgREST/RLS、保持ガード、Storageの実APIを使う。
- `pg_dump`をメモリー内で暗号化/復号し、誤鍵・改ざん拒否を確認。別DBへ `pg_restore` し、カタログと行数を照合する。
- 認証値は子プロセスの非公開pipeだけを通る。公開ログ/JSONに鍵・ダンプ・JWTは出さない。
- 自分で作成したスタックだけを停止する。ランナー破棄で架空データを削除する。

結果は `ci/v4-native-results-20261029` の `docs/native-ci-20261029/result.json` に別ジョブで保存する。
この記録ジョブだけにcontents:writeがあり、mainを変更する処理はない。
`FAIL` の試験を成功扱いしない。再実行前にsource_commitとfailed_stageを確認する。
Docker方式は配布元のダウンロード上限で失敗したため、公式nativeサービス配布へ切り替えた。

## 制限

PGのmajor 17を検証するが、本番の17.6.1.166とビルドは一致しない。
DBを同じ新規クラスタの別DBへ復元する試験であり、クラスタのglobal roles・サービス設定・Storageファイル量のバックアップ復元は別途必要。
nativeプロセスはランナーホストを共有し、コンテナによる外向き通信遮断ではない。
使用するのは架空データだけで、実バックアップや独立した第三者の署名の代わりにはならない。
実行全体20分、個別起動12分で打ち切る。失敗時もサニタイズした診断だけを残す。

ローカルホストの条件は [実行環境判定](../../docs/native-preflight-20261029.json)。
実データは [保管・鍵の決定票](../../docs/handover/backup-custody-decision-20261029.md) が先。
