## 安全な再構築の順序（実行前に依存関係を検証）
1. ローカルの隔離環境を用意。クラウド新規作成・課金・本番接続をしない。
2. 本番の現在の設定を読み取り専用で再取得し、GitHub保存定義との不足・差分を照合。
3. 拡張、スキーマ、型、シーケンス、テーブル、制約、索引、関数、トリガー、RLS、権限、cronの依存グラフを確定。循環依存を解消。
4. Auth関連の管理オブジェクトはSupabase標準構築物とアプリ独自定義を区別。標準管理オブジェクトを手作業で上書きしない。
5. ローカルで空DBを作成し、依存順にDDL適用。権限や SECURITY DEFINER の search_path を点検。
6. 通知・メール・LINE・cron・外部Webhooksを無効にして、架空データのみ投入。
7. ログイン、求人、応募、勤怠、RLSによる他人データ拒否、ロールバックを検証。
8. スキーマ・関数・権限・トリガー・cronの差分ゼロを確認。結果を日時・環境・コマンド・失敗件数付きで記録。

## バックアップ・復元の条件
- 実データを含むバックアップは公開GitHubへ置かない。暗号化、アクセス制御、鍵の別管理、保存期限を必須とする。
- DB、Auth、Storage実体、Edge Functions、環境変数、外部サービス設定を別々に棚卸しする。
- 個人情報を含む復元テストは隔離環境で実施し、外部送信を遮断する。
- RPO/RTO、バックアップ頻度、保管先、実行責任者、復元手順の承認を得るまで「復旧可能」と表示しない。
- 本番へのSQL適用、復元、課金変更、サービス停止、外部通知は事前承認が必要。

## 第三者への引き継ぎ合格条件
- 新担当者がチャット履歴なしで構成と契約・権限の所在を説明できる。
- 新担当者が隔離環境でゼロから構築・架空データで検証できる。
- バックアップを復元し、完全性・権限・通知停止を確認できる。
- 公開・切戻し手順とMFA・予備管理者・退任時の権限解除を確認できる。
- 各手順に証跡・責任者・未解決課題が記録されている。
