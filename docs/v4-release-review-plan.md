## DB修正案のまとまり

1. 匿名/他社名義の求人INSERT制限。
2. 勤務完了/打刻済み応募のDELETE制限。画面の削除件数ゼロ表示と組で扱う。
3. 旧企業登録RPCの公開実行権限整理、勤怠再計算の参加者認可。
4. 取消済み求人への応募と、応募時の不正な状態指定を拒否。

この4つを同時に入れたラボでも、正規の自社求人・本人応募・給与確認・QR打刻は成功。
ネイティブ環境で同じ順番を検証し、既存DDLとの差分をレビューして正式マイグレーションを作る。
CLIを用意した担当者が`--help`で仕様を確認し、`supabase migration new`等の正規手順を使う。
レビューSQLのROLLBACKを単にCOMMITへ書き換えて、そのまま本番に流さない。

## 紹介メールの切り替え案

停止用Edge Functionと、mailto方式の画面・新しいJS資産を一組で準備する。
本番承認後の実施順は、未認証の旧送信を止めるエンドポイント→画面・JS公開→実機確認を基本案とする。
切り替え途中の旧画面では紹介メール送信が失敗表示となる可能性があるため、実施時間と案内を決める。
紹介以外の通知用Resendキー・SMTP設定・LINE設定を削除/変更しない。
サーバーPOSTが410、APIキーの参照なし、画面から当該API要求なしを確認する。

メールアプリが未設定の場合は共有/QRを案内する。メールの配信完了とは表示しない。
障害時も停止用410は維持し、認証なしメール送信へ自動で戻さない。

## 適用後の受け入れ

- 匿名求人作成、他社求人作成、取消済み求人への応募、初期完了状態の指定が拒否される。
- 本人の通常応募と未打刻・応募中キャンセルが成功する。
- 完了済み応募と評価・勤怠修正履歴が保護され、件数ゼロの削除を画面が成功扱いしない。
- 未ログイン/他人/他社からの勤怠再計算が拒否される。
- 正規企業・本人・信頼されたサーバー処理、既存トリガー・給与確認・QRが成功する。
- 紹介メールは確認可能なメールアプリ画面を開き、サーバーの旧送信経路は停止している。
- DBカタログ・ACL・関数ハッシュ・画面公開コミット・Functions版・実施者・時刻を記録する。

実ユーザーへの通知が必要な確認は、宛先と内容を別途決めてから実施する。
今回のテストは実ユーザー・実受信先を使っていない。

## 切り戻しの区別

DB定義・権限の切り戻しは各レビューSQLの対応ファイルを使用する案である。
一部だけ適用された状態でまとめた戻しSQLを流さず、適用履歴を確認する。
ACL/関数を戻すと既知の問題も戻る。所有者と影響を判断する。
データ削除・退会の復旧はこれらSQLでは行えず、承認されたバックアップ復元手順が別に必要。
画面だけ戻す場合は差分をレビューしたrevertを追加し、履歴を消さない。

## 第三者への証跡

### 退会・日またぎ追加分の適用前確認

退会は保存期間を未決定のまま履歴を消さず、記録ありの自動削除を止める案。
運営が記録の保持・匿名化・削除・退会後の扱いを決め、ネイティブAuthで検証するまで適用しない。
新しい退会APIは保護RPCがなければ503で停止するため、承認後の切り替え案は以下とする。

1. 一時的に退会が利用できない時間を決め、案内する。
2. 個別プロフィールDELETEをしない新APIを先に配備する。RPC未導入なら必ず停止することを確認。
3. DBガード3件とサーバー専用RPCを正式マイグレーションで一括適用。
4. 記録ありの拒否・空アカウントの削除・後段エラー時の保持・セッション失効をネイティブAuth経由で確認。
5. 画面の案内を切り替え、一時停止を解消したことを確認する。

DBだけ先に入れて旧APIを動かし続ける方式は、複数プロフィールのある旧アカウント等で途中削除の余地があるため避ける。
戻す場合は先にAPIを停止し、ガードを解除する。元の破壊的な処理へ無条件に戻さない。
既存アクセスJWTが即時失効するとは表示せず、有効期限・敏感な操作の検証方針も確認する。
Storage等の所有物がある利用者のAuth削除条件も実環境で確認する。

日またぎ判定は通常のRLS・呼出し主体を維持する案。
実DBの複数接続で同じドライバーの同時応募、advisory lock待ち、再試行、勤務時間変更を確認する。
通知はモック競合試験だけで本番の一度だけ配信を保証せず、実DBのSKIP LOCKEDと実プロバイダーの条件を別途確認する。

最新版の入口はREADMEと`docs/v4-encrypted-backup-handover-20261029.md`。
ソースSHA256付きの`lab-result.json`、固定依存のlockfile、各レビューSQLと元定義を渡す。
Secretsの値はGitHubに含めず、安全な別経路で移管する。
チャット履歴なしで再実行・障害切り分け・復旧を第三者が実演するまで、完全引き継ぎ完了としない。
