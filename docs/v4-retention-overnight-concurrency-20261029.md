## 退会処理の現状と修正案

現行の取得済みコードは、本人確認後にドライバー/企業プロフィールを個別DELETEし、最後にAuth利用者を削除する。
プロフィールDELETEは応募・評価・勤怠修正履歴等へCASCADEする。
ラボでservice_roleによるプロフィールDELETEの後にAuth行が残り、業務履歴が消えることを再現した。
複数のHTTP操作に分かれているため、後続Auth削除が失敗しても前のDELETEを自動で戻せない構造だった。

保存期間・匿名化・退会後の閲覧権限は未決定なので、今回それらを独自に決めていない。
レビュー案は「業務記録があれば自動退会を止め、運営確認に回す」「記録がない場合だけ削除する」。
現在のデータに削除/匿名化を実行したものではない。

### DB側の保護案

`sql/review-v4-withdrawal-retention.sql`:

- driversに応募がある、companiesに求人がある場合はBEFORE DELETEで拒否する。
  authenticatedに限らず、通常のservice_role経路にも同じ保護をかける。
- Auth利用者のBEFORE DELETEで、業務記録のないプロフィールだけ削除する。
  同じDELETE文のトランザクションなので、後続のエラー時にプロフィール削除も戻る。
- サーバー専用`withdrawal_preflight(uuid)`は保護トリガー3件が有効かを確認。
  利用不可/運営確認/準備完了を返す。anon/authenticatedには実行権限を与えない。

Auth削除の後段でエラーを起こす架空トリガーを挿入し、空のプロフィールが先に削除されても
Auth行・プロフィールの両方が残ることを確認。エラーを除くと両方が削除されることも確認。
ただしこれは単一PostgreSQL DELETEの試験。GoTrue実装・supabase_auth_adminの権限まで再現したものではない。

### Edge Function・画面の準備

`delete-account/handler.ts`は、本人のgetUser結果だけを使い、リクエスト本文の利用者IDは使わない。

1. サーバー専用RPCで保護構成と業務記録を確認。RPC不在・停止・不明な応答は503で停止。
2. 記録があれば409で運営確認を案内。この段階ではセッション失効や削除をしない。
3. 記録がない場合はglobal signOutでリフレッシュセッションを失効させる案。
4. Authのhard DELETEを1回呼ぶ。Edge Functionからプロフィールを個別DELETEしない。
5. 失敗時は成功表示しない。DBから保持理由が返れば409、それ以外は503。

取得済みSDKとネイティブAuthでの結合試験は残る。特に、DBの拒否理由がGoTrueを通じて保持されるかは未確認。
理由が一般化されて返る場合もエラーとして止まり、成功扱いしない。
global signOut後に削除が失敗した場合、データは残っても再ログインが必要になる可能性がある。
リフレッシュセッションの失効は既存アクセスJWTの即時無効化と同じではなく、有効期限まで残り得る。
参考: [Supabase signOut仕様](https://supabase.com/docs/reference/javascript/auth-signout)。

driver/company画面も「すべての履歴を削除する」と断定する案内を改め、記録がある場合は運営確認を案内する。
HTTP失敗や保持拒否のときに成功表示/ローカルログアウト/画面遷移をしないことをモックで確認した。

## 日またぎ勤務

現行判定は同じwork_dateのstart_time/end_timeだけを比較していた。
「ある日の22時～翌2時」と「翌日の1時～5時」、同日開始の22時～翌2時と23時～翌1時を見逃すことを再現。

`sql/review-v4-overnight-overlap.sql`では終了時刻が開始時刻より早い場合に終了日を翌日として比較。
開始日が前後1日の有効応募を確認し、終了=次の開始の境界は重複としない。
登録の逆順でも拒否されること、取り消された勤務は重複対象外になることを確認。
同じドライバーの書き込み用にトランザクション単位のadvisory lockを用意した。

ただし複数DB接続でのロック待ち・デッドロック・トランザクション分離は未検証。
開始=終了の時間、24時間超を表す設計、企業による勤務時間変更等はこの試験の対象外。
RLSを回避するためにSECURITY DEFINERへ変更しておらず、既存の呼出し主体の可視性も別途確認が必要。

## 通知の競合試験

`supabase/tests/notification-interleavings.mjs`で、実際のワーカー関数をモックREST/プロバイダーへ接続して検証。
LINEワーカーは処理本体を関数へ切り出したが、HTTP入口の認証・送信処理・更新条件は維持した。

1. Aがattempt=1を取得し、プロバイダー応答を遅延させる。
2. リース期限切れをモデル化し、Bがattempt=2を取得して送信済みに更新する。
3. Aの成功または失敗応答を後から返す。
4. Aの古いPATCHが、stateとattemptsの条件不一致でBの送信済みを上書きしないことを確認する。

メール/LINEの計4ケースで同じ通知IDの重複防止キーを維持し、プロバイダーの冪等性をモデル化した受付は1回。
HTTP要求自体は2回発生しており、「要求が1回しか発生しない」とは言わない。
実プロバイダーの保証期間や障害時の実動作は実配信で確認していない。
DBのSKIP LOCKEDを複数セッションで検証したものでもなく、完全な一度だけ配信の保証ではない。
