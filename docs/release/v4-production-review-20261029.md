|ID|変更すること|利用者・運用への影響|適用判断に必要な追加確認|
|---|---|---|---|

|B|打刻済み・採用後・完了済み応募の削除を制限|未打刻の応募中/採用候補だけ取消可。削除0件を成功表示しない|本人/他人の取消、採用候補、勤怠・評価履歴の保持|
|C|旧企業登録権限の整理と勤怠再計算の認可|旧RPC利用があれば停止。本人/雇用企業/信頼されたサーバー以外は再計算不可|全呼出し元、既存トリガー、保守バッチ、給与・QR|
|D|取消求人への応募・不正な初期状態を拒否|通常の応募中登録は維持。旧データ連携の直接登録は拒否される可能性|確認画面からの通常応募、取消競合、既存給与保証処理|

|F|未認証の紹介メール送信を停止しメールアプリへ変更|旧紹介送信は410。利用者が自分のメールアプリから送信する|旧画面/キャッシュ、メールアプリなし、QR/共有、紹介以外の通知継続|

## 公開に伴う自動処理

- mainへの更新はPagesの公開につながる既存運用。資料だけのmain更新も公開契機として扱う。
- `.github/workflows/update-driver-experience.yml`はmainのpush全般で起動し、index.htmlを書き換えて追加pushするコードがある。
- `.github/workflows/offline-checks.yml`は公開と独立した検査で、検査失敗による公開停止は保証していない。
- Authメール/パスキーの変更ワークフロー、手動実行のパスワード設定、ソース書換えワークフローも存在する。

今回これらは変更・起動していない。検証ブランチ全体を一括マージしない。
承認する単位に必要な差分だけを用意し、mainの最終差分とワークフローの起動条件を再確認する。
共有ファイルdriver.html/company.html/index.htmlは複数単位を含むため、ファイル丸ごとのコピーで分割適用できるとは扱わない。
既存自動書換え処理を変更/停止する場合も、その差分を別途承認対象にする。

## 適用順序の案

全単位共通で、最新差分→隔離したネイティブ試験→暗号化退避/復元確認→戻し手順→所有者承認が先。
その後、A・B・Dを優先する案。C、F、E、Gはそれぞれの未完了条件を満たした単位ごとに分ける。
Hは関連する画面の差分として同時レビューする。日程や停止時間の数値は試験後に確定する。

|まとまり|実施順と途中状態|中断条件|
|---|---|---|
|A/B/D|必要な画面の変更→DBの正式マイグレーション→本人操作/拒否/履歴確認。Bの画面先行は0件を成功扱いしないため。旧キャッシュも含め確認|正常な自社求人・本人応募が拒否、履歴消失、旧画面が誤成功|
|C|全呼出し元の確認→DB権限/関数→通常登録・給与・QR確認|正規の再計算・登録経路・保守処理が失敗|
|F|旧送信を410で止めるFunction→index.htmlとintro-email.js→メールアプリ/共有確認。途中の旧画面では送信失敗になり得る|紹介以外のメール/LINEが失敗、サーバー送信が残る|
|E|停止時間を案内→新退会API（RPCなしなら503）→DBガード3件+RPCを一括→実Auth受入れ→画面案内→一時停止の終了確認|保護なしで削除できる、途中削除、記録あり削除、正規利用への想定外影響|
|G|複数接続・RLS試験→関数→日またぎ/隣接/同時応募確認|重複を許す、正規応募の拒否、ロック待ち/デッドロック|

EはDBだけ先行して旧APIを残さない。API切替直後の503は計画された一時停止として確認する。
記録あり409は想定動作で、問い合わせの担当/手順が必要。500/503の原因不明な増加は受け入れ失敗。
確認は隔離環境・架空アカウントが基本。本番の実データ変更・実送信を伴う試験は対象/手順も事前承認に含める。

## 障害時の停止と戻し方

|ID|準備された戻し候補|戻す際の条件・制約|
|---|---|---|
|A/B|review-v4-hardening-rollback.sql|2単位まとめたローカル用SQL。片方だけの適用なら該当部分だけの正式戻しSQLを新規レビューする|
|C|review-v4-legacy-and-rounding-rollback.sql|旧公開権限と関数を戻すため、既知の問題も戻る。代替は該当機能の停止|
|D|review-v4-application-entry-rollback.sql|取消求人/初期状態の拒否が外れる。新規応募の停止も検討|
|E|review-v4-withdrawal-retention-rollback.sql|先に退会APIを停止→確認後にガード解除。元の個別プロフィールDELETE方式へ自動で戻さない|
|F|停止用Functionを維持。画面はメールアプリ/共有の案内を修正|未認証サーバー送信へ戻さない。共通のResendキー/SMTP/LINEを削除しない|
|G|review-v4-overnight-overlap-rollback.sql|元の日内判定に戻る。夜勤の重複リスクが戻るので対象応募の停止/運営確認が必要|
|H|承認された画面差分だけをrevertで戻す|退会・削除0件等の表示まで古い挙動に戻らないか再確認。履歴を消すreset/force pushはしない|

戻しSQLはデータ復旧ではない。退会済みアカウント/削除済み履歴はSQLの切り戻しで復元できない。
誤削除時は追加書込みを止める範囲を決め、暗号化バックアップの隔離復元・差分照合から復旧を判断する。
本番DB全体の巻き戻しは新しい正常データも失うため、自動実行しない。
各段階で適用済みID・マイグレーション・Function版・公開コミットを記録し、部分適用状態を維持したまま原因を切り分ける。
