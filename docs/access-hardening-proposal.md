# 第4版 アクセス制御・紹介メールの改善案
2026-10-27。レビュー用。Pro変更はユーザー意向で見送り。既存サイト・DBを継続。

## 調査と適用の区別
本番カタログ・関数定義・権限・ポリシーと、mainのHTML/JavaScriptを読み取り確認した。登録・打刻・通知の実行はしていない。本書およびSQL案は本番未適用。バックアップと通知停止した検証環境を準備し、検証後に本番変更を説明する。

## 優先1: 旧企業登録経路
companiesの自己所有者向けポリシーに加え、anon/authenticatedにINSERT WITH CHECK trueの旧ポリシーが残存。register_companyも両ロールが実行でき、定義内に本人確認・user_idの紐付けがない。現在のHTML/JavaScriptの全ファイルでこのRPC呼出しは見つからなかった。ただし外部クライアント・他スキーマ等の依存まで否定していない。
提案: 旧ポリシーを削除し、anonの直接INSERTと旧RPCの公開実行権限を取り除く。authenticatedの自己所有者ポリシーは残す。register_companyの定義自体は消さない。新規企業のメール確認後登録、既存企業ログイン、求人登録を検証する。

## 優先2: 勤怠再計算
apply_attendance_roundingはSECURITY DEFINERでanon/authenticatedから実行可能。定義に利用者本人・所属企業の確認がない。
ただしattendance_rounding_triggerがこの関数を呼び、トリガー関数はSECURITY INVOKER。単純なEXECUTE剥奪は通常打刻のトリガーも失敗させる可能性があるため実施しない。
提案: 所有する企業または該当ドライバーの勤務に限定する認可を検討。トリガー経路と直接RPC経路を分ける案も比較する。退会・バッチ・service_role・夜勤・手動修正を含め検証し、更新結果がないことを含む拒否テストを用意してからSQLを確定する。

## 優先3: 紹介メール
トップ画面の「メールで紹介」は未ログイン利用者が宛先を入力し、share-driver-spot-emailへ送信。取得した本番コードには利用者認証・送信回数制限・ボット検証がない。CORSは認可の代わりにならない。
選択肢:
1. 推奨する当面案: サーバーからの紹介送信をやめ、利用者のメールアプリで固定の紹介文とURLを開く方式。フォームの案内・成功表示も変更する。自動送信メールの悪用経路を閉じるためEdge Function側も同時に停止する必要がある。トップ画面だけの変更では対策完了としない。
2. サーバー送信を維持: ボット検証、送信元/IP/宛先/全体の原子的回数制限、送信上限、エラー時の扱いを実装。送信サービス障害・並列アクセスも検証する。
どちらも利用者の体験が変わるので、具体的な画面変更と切戻しを用意して説明する。現時点で本番メール送信・停止はしていない。

## 検証条件
- 未ログイン・他社・他人のアクセスは拒否され、データ変更がない。
- 正規企業のメール確認後登録、本人プロフィール取得、求人作成は成功する。
- 通常打刻・手動修正・日またぎの勤怠計算が成功する。
- メール・LINEは外部送信しない検証環境で試す。
- カタログの事後照合だけで実動作検証の代わりにしない。

## 残る作業
全RLSポリシーと全Functionsの認可監査は未完了。本書は上記入口の重点確認結果であり、システム全体の安全性保証ではない。無料で取得するバックアップ方式も、Auth・スキーマ・権限・データの範囲と安全な保管先を確定する必要がある。
