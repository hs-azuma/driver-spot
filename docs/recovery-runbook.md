# 障害・バックアップ・復旧手順（確認待ち事項を含む）

この文書は復旧完了の証明ではない。2026-10-27にFreeプランには定期バックアップが含まれないことを管理画面で確認。ユーザー意向によりPro変更は見送り。外部・手動バックアップの有無と復元可能性は未確認。無料での暗号化バックアップ・ローカル復元手順の整備は未完了。

## 初動
1. 発生時刻、画面URL、症状、直前のコミット、影響範囲を記録。個人情報や認証トークンを共有資料へ載せない。
2. GitHub Pages公開履歴、Supabase稼働状態・ログ、認証、通知サービスを順に確認。
3. 誤送信などの場合は、対象の処理を特定して停止案を提示する。DB全体の停止・復元を先に行わない。

## 画面だけの切り戻し
動作していたコミットを特定し、差分をレビューしたrevertを新しいコミットとして公開する。
履歴を消すforce pushをしない。DB・認証設定の変更は画面のrevertでは戻らない。
公開成功と対象画面を確認する。

## DB復旧を可能にするための事前整備
- 所有者がSupabaseのプラン、定期バックアップ、PITRの利用可否と保持期間を確認。
- 許容データ損失（RPO）と復旧時間（RTO）を決定。現時点で保証値はない。
- スキーマ・関数・RLS・トリガー・権限・定期実行・Auth設定・Edge Functions設定を記録。
- DBバックアップとは別にStorage実ファイルと秘密情報の安全な復旧手段を確認。
- 個人情報を含むバックアップは暗号化・アクセス制限・保存期限を設け、公開GitHubへ置かない。
- 検証環境へ復元し、ログイン、所有者別アクセス、求人、応募、勤怠、通知停止を検証する。
- 復元で古い通知キューを再送しない手順を用意する。

## 本番DBを復旧する際
対象・復元時点・失われるデータ・サービス停止時間を提示し、所有者の承認後に実施する。
実施者、開始終了、対象、検証結果を記録する。移管先の担当者が独力で復旧できることを最終条件とする。
