## 暗号化復元の範囲

`tools/restore-lab/backup-envelope.mjs`はNode標準のAES-256-GCMとscryptを使う。
テストでは毎回ランダムな試験用パスフレーズ、salt、nonceを作成する。
ヘッダーを認証付きデータに含め、形式を固定し、サイズ上限と復号後のファイルSHA256を検査する。

|同梱ファイル|内容|
|---|---|
|database.pglite.tgz|その場で構築した架空PGlite DB|
|application-review.sql|保存定義から生成した再構築候補|
|restore-manifest.json|再構築候補の件数・SHA256・除外範囲|
|settings-fixture.json|Auth/Storage/Secretsを含まないことを示すひな形|

復号したDBから、既存と同じカタログ・権限・架空求人・企業名・自動採番の継続を確認した。
復元試験の処理には本番接続文字列・認証キー・本番バックアップの入力口を用意していない。
鍵・平文バックアップ・暗号化実体はメモリ上で扱い、保存しない。結果に残すのは検査結果・サイズ・SHA256等だけ。
JSの全メモリを完全消去したことを保証するものではなく、実バックアップの鍵管理は別途必要。

数MBのデータで正規表現によるBase64検査が停止する問題を実行試験で検出したため、
文字種・長さ・正規化後の一致を調べる方式へ修正し、2MBのバイナリを検査する回帰テストも追加した。

この形式は架空データ検証用であり、ネイティブSupabaseのpg_dump/pg_restore、実Auth、Storage実体、
Secrets、cron、メール/LINEの設定を復旧したものではない。実運用前の暗号設定/鍵管理レビューも残る。

## 別フォルダ再現

```sh
python3 -B scripts/verify-handover.py
```

スクリプトはソースのファイルSHA256からフィンガープリントを作り、一時フォルダで以下を実行する。

1. `npm ci --prefix tools/restore-lab --ignore-scripts --offline --no-audit --no-fund`
2. `npm test`
3. `npm --prefix tools/restore-lab test`

既存のnode_modules・.gitはコピーしない。秘密設定ファイルや外部へのシンボリックリンクも取り込まない。
依存は既存のnpmキャッシュからlockfileに従って導入し、ネットワークへの自動フォールバックはしない。
初めてのPCでは公開パッケージの取得またはキャッシュの事前準備が必要。
Nodeは.nvmrcの24.22.1、Pythonは3.12を確認する。

テスト後に一時フォルダを削除し、コマンド・終了コード・所要時間・ソース/出力SHA256・検証件数をJSONに保存。
生成された検証結果自身はソースのフィンガープリントから除外し、結果更新による循環を避ける。
失敗した場合はFAILを記録し、前回の成功を最新結果として残さない。

同じ実行ホストでの再現であり、別OS・別担当者・完全に未設定のPCでの受け入れ確認ではない。
Docker/psql/Supabase CLIの有無も記録する。ネイティブSupabaseの起動や本番接続はしない。

## 実データバックアップの計画

[計画ファイル](backup-recovery-plan.json)は`REAL_BACKUP_NOT_CONFIGURED`。
保管先・鍵の管理者/保管先・保持期限・復旧目標・担当者を未定のまま明示している。
試験成功をもって、実データが保存された/復旧できるとはしない。

|対象|実バックアップで確認する内容|
|---|---|
|DB|スキーマ、全対象データ、関数/ACL/トリガー、シーケンス、役割・拡張|
|Auth|利用者/identities、設定、認証サービス版、セッションと秘密値の復旧方針|
|Storage|メタデータと実ファイルの両方|
|Functions|ソース、実行設定、呼び出し元、認可、固定バージョン|
|外部設定|Secrets/Vault、DNS、Resend/LINE、スケジュールと通知再開方法|

実データは公開GitHubへ置かず、暗号化した保管先と鍵へのアクセスを独立して管理する。
運営側で保管先・鍵管理・責任者・期限を決め、隔離したネイティブ環境で復元してから復旧可能と判断する。
復元中は通知・cron・外部フックを停止し、古い通知の再送を防ぐ。
