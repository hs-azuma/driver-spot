## 今回の完成基準

1は架空ユーザーの画面登録・求人掲載・応募・採用・QR打刻・給与確認/承認を実SDK/実Auth/実DBへ通すこと。
企業は架空fixtureで用意します。掲載・採用後に架空求人の日時だけを正規企業権限で現在へ移し、勤務開始前の申請制限を守って検証します。実運用の日時変更手順ではありません。企業メール認証の実受信、カメラ、生体認証、通知配信は含めません。
2は10 Functionsをstrictで型検査し、直接・間接依存の解決内容も固定すること。起動smokeとは分けます。
3は今回の4つの型参照とFunction依存を固定し、lockfile更新を通常実行で拒否すること。
4/7は承認前に実行しないレビュー可能な改善案・運用案を仕上げること。運用開始を完了扱いにしません。
5/6はツールを架空ファイル/隔離DBで検証すること。実バックアップや本番診断の実行ではありません。
8は入力ソースと成功証拠を照合し、未完了・承認待ちを明示して次の担当者が再開できること。

## 残る承認・外部確認（今回の8項目外）

- 鍵管理者・鍵保管・保存期間・実行担当、許容データ損失時間と復旧目標時間の確定。
- 実データの暗号化バックアップと、個人情報を保護した実復元確認。
- 管理権限/MFA/予備管理者、独立した第三者の署名・実演。
- 本番差分・承認範囲・担当者・日時・停止/切り戻しの確定。
- 実iPhone/Android、実メール/LINE、別物理ホスト、旧Storage UUID/URL、外部サービスと秘密値。

担当者・日数・承認は未指定のまま保持します。追加契約・有料リソース・mainへのマージは行いません。
